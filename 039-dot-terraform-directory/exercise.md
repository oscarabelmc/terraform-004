# .terraform/ Directory Exercise

**Exam Question:** You are reviewing Terraform code from a colleague and discover a `.terraform/` directory. What is the purpose of this directory?

## Background

When you run `terraform init`, Terraform creates a `.terraform/` directory in the working directory. This directory stores **local working data** — it is not committed to version control and can be regenerated by re-running `terraform init`.

## Steps

### Part 1 — Start with a clean state

1. **List the current directory contents:**

   ```bash
   ls -la
   ```

   No `.terraform/` directory exists yet. The config files are all that's present.

### Part 2 — Run terraform init

2. **Initialize the working directory:**

   ```bash
   terraform init
   ```

3. **Examine what was created:**

   ```bash
   ls -la .terraform/
   ```

   ```
   .terraform/
   ├── providers/
   │   └── registry.terraform.io/
   │       └── hashicorp/
   │           └── random/
   │               └── 3.6.0/
   │                   └── linux_amd64/
   │                       └── terraform-provider-random_v3.6.0_x5
   └── modules/
       └── modules.json
   ```

### Part 3 — Examine each component

4. **Provider plugins:**

   ```bash
   ls -R .terraform/providers/
   ```

   Terraform downloads provider plugin binaries and stores them here. Each provider version gets its own directory. This is **not** the global plugin cache — it's a local copy for this working directory.

5. **Module metadata:**

   ```bash
   cat .terraform/modules/modules.json
   ```

   This file records which modules are used, their sources, and versions. If you use local modules, they are symlinked or copied here.

6. **Backend metadata:**

   ```bash
   cat .terraform/terraform.tfstate
   ```

   If using a remote backend, this file stores metadata about the backend connection (state location, locking info, serial). It is **not** the actual state file — the real state is in the remote backend.

### Part 4 — Understand what .terraform/ is NOT

7. **Check where the actual state is:**

   ```bash
   ls -la terraform.tfstate 2>/dev/null || echo "No local state (using remote backend)"
   ```

   With a local backend, `terraform.tfstate` is in the **working directory**, not inside `.terraform/`. The `.terraform/` directory never contains the actual state file.

### Part 5 — .gitignore

8. **Check why .terraform/ is not committed:**

   ```bash
   cat ../.gitignore 2>/dev/null || echo "No .gitignore found"
   ```

   Standard practice is to add `.terraform/` to `.gitignore`:

   ```
   .terraform/
   *.tfstate
   *.tfstate.backup
   ```

### Put It Together

You are reviewing Terraform code from a colleague and discover a `.terraform/` directory. What is the purpose of this directory?

- A. The `.terraform/` directory stores Terraform's local working data, including installed provider and module plugins and backend metadata
- B. The `.terraform/` directory stores the Terraform state file
- C. The `.terraform/` directory stores Terraform configuration files
- D. The `.terraform/` directory stores Terraform logs
- E. The `.terraform/` directory stores backups of previously applied configurations
