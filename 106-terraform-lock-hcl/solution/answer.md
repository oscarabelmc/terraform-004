# Answer

The correct answer is **B**.

> A dependency lock file used by Terraform; it is created or updated every time you run `terraform init`.

---

## Why B Is Correct

`.terraform.lock.hcl` is Terraform's **dependency lock file**. It records the exact version and cryptographic checksums of every provider installed by `terraform init`.

### When it's created or updated

| Event | Lock file action |
|-------|-----------------|
| **First `terraform init`** | Created with current provider versions |
| **`terraform init` with unchanged providers** | No change (versions match) |
| **`terraform init` after adding a provider** | New provider entry appended |
| **`terraform init -upgrade`** | Updated to latest matching versions |
| **`terraform init` after removing a provider** | Entry removed |

The key: **every `terraform init`** evaluates whether the lock file needs updating. If providers match, it's untouched. If anything changed, it's updated.

### What the lock file contains

```hcl
provider "registry.terraform.io/hashicorp/random" {
  version     = "3.6.3"
  constraints = "~> 3.6"
  hashes = [
    "h1:fXq9E8w+6Vj6iR32/b7RUI50P0R6SDXc7mfhnYpGq0=",
    "zh:123...",
    ...
  ]
}
```

| Field | Purpose |
|-------|---------|
| `version` | The exact provider version installed |
| `constraints` | The version constraint from `required_providers` |
| `hashes` | Checksums for integrity verification (multiple for cross-platform) |

## Why the Others Are Wrong

| Option | Why it's incorrect |
|--------|-------------------|
| A — Configuration file created by `plan` | `terraform plan` does **not** create or modify the lock file. Only `init` does. The lock file is also not a configuration file — it's an output generated by `init`. |
| C — State backup from `apply` | State backups use the `.backup` suffix (`terraform.tfstate.backup`). `.terraform.lock.hcl` is unrelated to state. |
| D — API call log | The lock file records **provider checksums and versions**, not API call logs. API logging is controlled by `TF_LOG`. |
| E — Module cache | Modules are downloaded to `.terraform/modules/`. The lock file tracks **providers only**, not modules. |

## Lock File Analogy

| System | Lock file | Purpose |
|--------|-----------|---------|
| **Terraform** | `.terraform.lock.hcl` | Lock provider versions |
| **npm** | `package-lock.json` | Lock npm package versions |
| **Cargo** | `Cargo.lock` | Lock crate versions |
| **Go** | `go.sum` | Verify module checksums |

## Commit Policy

```
✅ DO commit:     .terraform.lock.hcl
❌ DO NOT commit: .terraform/ (local cache, binaries)
❌ DO NOT commit: terraform.tfstate (secrets, frequent changes)
```

Committing the lock file ensures:
- **CI/CD** installs the same provider versions as local development
- **Team members** get identical provider versions
- **Audit trail** of provider version changes in Git history

## Upgrading Providers

```bash
# Normal init — respects lock file
terraform init

# Upgrade — ignores lock file, fetches latest matching, updates lock
terraform init -upgrade
```

Without `-upgrade`, `init` uses the versions in the lock file. With `-upgrade`, it fetches the newest versions matching the constraint and updates the lock file.

## Exam Tips

- **Lock file = provider version lock** (like `package-lock.json` for npm)
- Created/updated by **`terraform init` only** — not `plan`, `apply`, or `validate`
- **Commit it to version control** — ensures reproducible builds
- Tracks **providers only**, not modules
- Use `terraform init -upgrade` to update to newer matching versions
- Common exam trap: confusing `.terraform.lock.hcl` with `.terraform/` directory or `terraform.tfstate`
- Another trap: thinking `plan` or `apply` modifies the lock file — only `init` does
